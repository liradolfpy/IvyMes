## 1. Purpose

This document defines the project convention for:

1.  System-generated identifiers used by project entities.
2.  Uniqueness scope of system identifiers.
3.  Storage of identifiers originating from external systems.
4.  Human-readable business numbers.
5.  Assignment and uniqueness rules for business numbers.
6.  Uniqueness constraints on fields.
7.  Validation of references between project collections.
8.  Lifecycle behavior when a referenced entity is updated, retired, or
    removed.

The purpose is to ensure that collection designs remain consistent,
traceable, maintainable, and suitable for the project database architecture.

This document is intended to be used together with:

-   `00_Project_Control\Project_Instructions.md`
-   `00_Project_Control\Decisions_Log.md`
-   `01_Requirements\CollectionNamingConvention.md`

## 3. Scope

This convention applies to project collections that contain:

-   Master data
-   Configuration data
-   Transaction data
-   Reference data
-   Relationship data
-   Operational data

It covers both:

-   System identifiers used for technical references.
-   Human-readable identifiers used by users and business
    processes.

It does not define the detailed field structure of individual
collections.

# 4. Identifier Concepts

The project shall distinguish between the following identifier concepts.

  -----------------------------------------------------------------------
  Identifier                          Purpose
  ----------------------------------- -----------------------------------
  System ID                           Technical identifier for a system
                                      entity

  Business Number                     Human-readable identifier used by
                                      users/business processes

  External ID                         Identifier originating from another
                                      system

  Reference ID                        System ID used to refer to another
                                      project entity
  -----------------------------------------------------------------------

These identifiers shall not be treated as interchangeable.

# 5. System IDs

## 5.1 Purpose

Every persistent project entity shall have a system-generated `_id`.

The system ID is intended for:

-   Internal references
-   Referential integrity
-   Technical identification
-   API references
-   Database operations
-   Relationship management

The system ID shall not normally be used as the primary human-facing
business number.

## 5.2 ID Format

Use the ID type, format, and uniqueness scope defined in `00_Project_Control/Project_Context.md`. Examples below illustrate one possible string-ID convention; they do not prescribe its length for every project. Database-default identifiers may be used only when consistent with the project's selected ID convention.

The exact generation mechanism remains OPEN and must be defined and documented before it is relied upon.

## 5.3 ID Generation

System IDs shall be generated by a controlled project-wide ID generation
mechanism.

The generation mechanism must guarantee that two active or historical
entities cannot unintentionally receive the same system ID.

When project context require database-wide uniqueness, apply:

> **System IDs shall be globally unique across the project database, not
> merely unique within an individual collection.**

This allows a system ID to unambiguously identify an entity without
requiring the collection name as part of the identifier.

Example:

``` text
1000293847561029
```

shall identify one entity only.

## 5.4 ID Immutability

Once assigned, a system ID shall be immutable.

A system ID shall not be changed because:

-   The entity name changes.
-   The entity business number changes.
-   The entity moves to another plant.
-   The entity is retired.
-   An external system changes its identifier.

If an entity is logically retired, its system ID remains associated with
its historical records.

# 6. External System Identifiers

## 6.1 Principle

Identifiers originating from external systems shall be stored separately
from project system IDs.

An external identifier must never replace the project `_id`.

Example:

``` javascript
{
    "_id": "1000293847561029",
    "productNo": "PRD-000125",
    "productName": "Transmission Housing",
    "sapMaterialId": "10004567"
}
```

The project `_id` remains the authoritative project identifier.

The external identifier is retained for integration and reconciliation.

## 6.2 External Identifier Fields

Where an entity is integrated with an external system, use explicitly
named fields.

Examples:

``` text
sapMaterialId
sapWorkOrderId
erpCustomerId
plcMachineId
scadaEquipmentId
externalProductId
```

The exact field name shall follow the project key naming convention.
For scalar references to one entity, the referenced-entity stem shall be grammatically singular under DATA-003. Repeated references shall follow project modeling rules; when flat modeling is selected, use separate relationship records. Do not pluralize scalar reference keys to imply multiplicity. See `KeyNamingConvention.md` for the singularization and ID/display-value pairing rules.

## 6.3 External Identifier Uniqueness

External identifiers shall normally be unique within the scope of their
originating system.

For example:

``` text
externalSystem = SAP
externalId = 10004567
```

is different from:

``` text
externalSystem = ERP-X
externalId = 10004567
```

Therefore, where multiple external systems can be integrated, uniqueness
may require the combination:

``` text
externalSystem + externalId
```

or an equivalent system-specific field structure.

## 6.4 External Identifier Changes

External identifiers shall not cause the project system ID to change.

If an external system changes its identifier:

1.  The project system ID remains unchanged.
2.  The external identifier is updated according to the integration
    rules.
3.  Historical integration/audit information shall be preserved where
    required.
4.  Existing project references shall continue to use the project system ID.

# 7. Human-Readable Business Numbers

## 7.1 Purpose

Business numbers are identifiers intended for:

-   Operators
-   Supervisors
-   Planners
-   Quality personnel
-   Maintenance personnel
-   Reports
-   Labels
-   Documents
-   Customer or supplier communication where applicable

Business numbers are separate from system IDs.

Example:

``` javascript
{
    "_id": "1000293847561029",
    "workOrderNo": "WO-2026-000001"
}
```

## 7.2 Entities Requiring Business Numbers

The following entities will normally require human-readable business
numbers where they participate directly in manufacturing or business
workflows:

### Production

-   Work Order
-   Production Order
-   Production Entry, if user-facing
-   Batch
-   Lot
-   Serial Number

### Product and Material

-   Product / Part
-   Material
-   Product Revision, where required
-   BOM
-   Routing

### Quality

-   Inspection Request
-   Non-Conformance
-   Corrective Action, where required

### Maintenance

-   Maintenance Request
-   Maintenance Order

### Commercial / Enterprise Integration

-   Customer
-   Supplier
-   Sales Order
-   Purchase Order, where within project scope

Not every technical/reference collection requires a human-readable
business number.

For example, a Reason Code or UOM may use a controlled code rather than
a sequential business number.

The exact requirement for each collection shall be recorded in its
collection specification.

# 8. Business Number Assignment

## 8.1 General Rule

Business numbers shall be assigned by a controlled numbering rule.

A business number should be:

-   Human-readable
-   Stable
-   Unique within its defined scope
-   Suitable for display and communication
-   Independent of the technical system ID

## 8.2 Recommended Pattern

Where appropriate, business numbers may use:

``` text
<PREFIX>-<YEAR>-<SEQUENCE>
```

Example:

``` text
WO-2026-000001
WO-2026-000002
```

The actual numbering pattern shall be defined by the relevant collection
specification.

## 8.5 Project-Specific Numbering Rules

Read the project's numbering table in `00_Project_Control/Project_Context.md`. It defines business-number patterns, requiredness, uniqueness scopes, and revision lineage rules. Do not infer a universal numbering pattern from an example. The existing project numbering baseline is retained there.

## 8.3 Sequence Generation

Business-number sequences shall be generated using a controlled sequence
mechanism.

The mechanism must prevent duplicate assignment under concurrent
creation requests.

The design shall not depend on application-level assumptions that are
unsafe under concurrent transactions.

## 8.4 Business Number Immutability

Unless a specific business rule permits correction, a business number
shall be immutable after creation.

A change to descriptive master data shall not normally cause a business
number to change.

# 9. Uniqueness Rules

## 9.1 General Principle

Uniqueness shall be explicitly defined for important fields.

Every collection specification shall identify:

-   Unique fields
-   Composite unique fields
-   Scope of uniqueness
-   Whether uniqueness applies to active records only or to all records

## 9.2 System ID

The system `_id` shall be unique within the scope defined by project context. If that scope is database-wide, enforce uniqueness across collections and historical records.

It shall not be reused after retirement or deletion.

## 9.3 Business Number

Business-number uniqueness shall be defined according to the business
domain.

The default principle is:

> A business number shall be unique within the smallest business
> boundary in which the number is intended to identify an entity
> unambiguously.

Possible boundaries include:

-   Global project
-   Tenant
-   Site
-   Plant
-   Company
-   Business Unit
-   Production Line

The scope must be explicitly documented for each collection.

## 9.4 Plant-Scoped Numbers

Where a business number is meaningful only within a plant, uniqueness
may be scoped by plant.

Example:

``` text
plantId + workOrderNo
```

could be unique.

This allows:

``` text
Plant A / WO-2026-000001
Plant B / WO-2026-000001
```

if the business process permits the same number in different plants.

## 9.5 Globally Unique Numbers

Where an entity is referenced across plants, sites, or systems, the
business number should normally be globally unique.

Examples may include:

-   Serial Number
-   Customer-facing identifier
-   Certain product numbers
-   Enterprise-wide material numbers

The exact scope shall be determined by the business requirement.

# 10. Uniqueness Constraint Specification

Every collection specification should document uniqueness using a table
such as:

  ---------------------------------------------------------------------------------------
  Field / Combination                            Unique Scope            Applies To
  ------------------------------- --------------------- ---------------- ----------------
  `_id`                                             Yes Global project       All records

  `workOrderNo`                                     Yes Plant            Active +
                                                                         historical

  `productNo`                                       Yes Global           All active
                                                                         products

  `externalSystem + externalId`                     Yes External system  Active mappings
  ---------------------------------------------------------------------------------------

Where MongoDB indexes are used to enforce uniqueness, the corresponding
index requirement shall be documented in the collection specification.

## 10.1 Soft-Deleted / Retired Records

The treatment of retired records must be explicit.

The default proposed rule is:

> Historical identifiers shall not be reassigned merely because the
> original entity is retired.

This prevents historical records from becoming ambiguous.

If a business process requires identifier reuse, it must be explicitly
current and the uniqueness rule must define the mechanism.

# 11. Reference Management

## 11.1 Reference Principle

References between collections shall use the project system ID.

Example:

``` javascript
{
    "productId": "1000293847561029",
    "productName": "Transmission Housing"
}
```

The `productId` is the technical reference.

The `productName` is intentionally stored as a flat denormalized display
value in accordance with the project's data-modeling convention.

## 11.2 Mandatory ID + Name Pairing

For referenced master entities, the default project convention is:

``` text
<entity>Id
<entity>Name
```

Examples:

``` text
plantId
plantName

productId
productName

workCenterId
workCenterName

createdById
createdBy

updatedById
updatedBy
```

Both fields shall normally be present together.

This denormalization is intentional and is used to reduce runtime
`$lookup` requirements and support efficient project UI/reporting queries.

## 11.3 Reference Validation

Before creating or updating a record containing a reference:

1.  The referenced entity must exist.
2.  The referenced entity must be valid for the intended operation.
3.  The referenced entity's system ID must be valid.
4.  The denormalized Name value should correspond to the referenced
    entity at the time of transaction creation/update.
5.  Business rules governing plant/site/domain compatibility shall be
    checked where applicable.

## 11.4 Cross-Domain Reference Validation

Where an entity is site- or plant-specific, the reference shall be
validated against the appropriate organizational boundary.

Example:

A WorkOrder belonging to Plant A should not reference a WorkCenter
belonging to Plant B unless a current cross-plant rule explicitly
permits it.

# 12. Update, Retirement and Removal of Referenced Entities

## 12.1 Update of Referenced Entity Name

Because the project uses strategic denormalization, updating a master
entity's name creates two considerations:

1.  The authoritative master record changes.
2.  Existing transactional records may contain a historical denormalized
    copy of the name.

The default proposed rule is:

> Transactional records shall preserve the descriptive value that was
> valid when the transaction occurred unless the project explicitly
> defines a synchronization rule.

Example:

A WorkCenter is renamed:

``` text
Before:
Machining Center 01

After:
CNC Machining Center 01
```

Historical WorkOrders may retain:

``` text
workCenterId: "..."
workCenterName: "Machining Center 01"
```

while new WorkOrders use:

``` text
workCenterId: "..."
workCenterName: "CNC Machining Center 01"
```

This preserves historical reporting context.

For master/configuration collections, controlled propagation may be used
where required.

## 12.2 Retirement

Entities that are no longer available for new transactions should
normally be **retired/inactivated rather than physically deleted**.

Example:

``` javascript
"active": false
```

or the project's current lifecycle/status field.

The exact field shall follow the collection specification.

A retired entity:

-   Remains available for historical references.
-   Cannot normally be selected for new transactions.
-   Continues to retain its project system ID.
-   Must not have its system ID reassigned.

## 12.3 Physical Deletion

Physical deletion of an entity referenced by historical transactions
should normally be prohibited.

Deletion may be permitted only when:

-   No dependent records exist, or
-   The project has an explicit data-retention/deletion rule, or
-   The entity is proven to be erroneous/test data and safe to remove.

Before physical deletion, dependency/reference checks shall be
performed.

## 12.4 Orphan Prevention

The system should prevent creation of new orphan references.

An orphan reference is a reference whose target entity does not exist.

Examples:

``` text
WorkOrder.productId
```

pointing to a non-existent Product.

Such references should be rejected during validation.

# 14. Reference and Denormalized Name Consistency

Because both ID and Name are stored, the system must distinguish
between:

### Authoritative value

The master collection owns:

``` text
productId
productName
```

### Transactional snapshot

A transaction may contain:

``` text
productId
productName
```

The transaction's `productName` is a denormalized snapshot intended for
fast access and historical context.

The existence of a matching `productId` does not imply that the current
master name must always equal the historical transaction name.

This distinction shall be documented wherever historical snapshots are
important.

A WorkOrder may contain:

``` javascript

    "_id": "1000293847561029",

    "workOrderNo": "WO-2026-000001",

    "plantName": "Bangalore Plant",

    "supervisorId": "5566778899001122",
    "supervisorName": "Rajesh Kumar",

    "createdAt": ISODate("2026-04-28T10:20:00.000+0000"),
    "createdById": "6688990011223344",
```

The document remains completely flat.

No referenced master entity is embedded as a nested document.

# 16. Example --- External Integration

An integrated Product record may contain:

``` javascript
{
    "_id": "9876543210123456",
    "productNo": "PRD-000125",
    "productName": "Transmission Housing",

    "sapMaterialId": "10004567",
    "sapMaterialName": "TRANSMISSION HOUSING"
}
```

The project `_id` remains the project identifier.

The SAP identifier remains an external-system identifier.

The two must not be treated as the same identifier.

# 22. Final Directive

All project collection designs shall clearly distinguish:

> **System identity, business identity, external identity, and reference
> identity.**

System IDs shall remain stable and technically authoritative.

Business numbers shall be human-readable and governed by explicit
numbering and uniqueness rules.

External identifiers shall remain separate from project identifiers.

References shall be validated and shall not create orphan records.

Referenced entities shall normally be retired rather than physically
deleted when historical transactions depend on them.

Apply the document structure and reference display-pair rules defined in project context settings, preserving stable technical identity and explicit reference semantics. Examples illustrate flat denormalization; they do not select that modeling policy for every project.
